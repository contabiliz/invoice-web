# Spec 02.1: Upload Batch — Máquina de Estados e Orquestração

## 1. Overview

Esta especificação define o comportamento do estado interativo e a orquestração do upload em lote para arquivos fiscais (PRD-02). 

Como os arquivos carregados pelo usuário (`File` / `FileList` nativos do browser) não são serializáveis, todo este módulo é executado prioritariamente no lado do cliente usando a diretiva `"use client"` do Next.js. O layout inicial, SSR e configuração de layout são feitos pelo servidor, mas a máquina de estados que governa os uploads deve rodar na thread do browser.

Responsabilidades do módulo:
- Manter o estado consolidado de cada arquivo selecionado (tipos de dados, status individual, progresso).
- Controlar as transições de estado do Batch como um todo (9 fases conforme PRD §02.4.1).
- Gerenciar a fila de concorrência definida no PRD (limite de 4 uploads paralelos).
- Despachar ações de side effect (presign, PUT para storage, confirm).

Responsabilidades excluídas:
- Chamadas de rede puras e autenticação, que pertencem à spec `02.2-upload-api-client.md`.
- Renderização visual e JSX, tratados na spec `02.3-upload-components.md`.

## 3. Architecture Decision Records (ADRs)

### ADR-001: Estado Normalizado em Map (`Record<string, FileItemState>`)

- **Context:** Precisamos rastrear o status de até 500 arquivos simultaneamente. Cada arquivo tem progresso individual, URL de presign, falhas e possível renovação de URL.
- **Decision:** Utilizar um **dicionário normalizado** `Record<internalId, FileItemState>` com array separado `fileIds: string[]` para ordem, em vez de array contínuo.
- **Reasons:**
  - Atualização `O(1)` do progresso de um arquivo sem iterar sobre 500 registros até 10x por segundo.
  - Facilita lookup direto no confirm sem `.find()`.
- **Consequences:** O estado precisa de geração de ID interno (`crypto.randomUUID()`) na seleção via DropZone.

### ADR-002: Next.js App Router — Server Component como shell, Client Component como orquestrador

- **Context:** Arquivos (`Blob`/`File`) violam os princípios de serialização SSR. O layout inicial pode ser SSR para TTFB rápido.
- **Decision:** `UploadPage` é Server Component (shell + metadados). `UploadView` é Client Component com `"use client"` — contém todo o estado interativo.
- **Reasons:** Arquivos nativos do browser não cruzam o boundary servidor→cliente. Componentes com hooks e event handlers devem ser Client Components no App Router.
- **Consequences:** O hook `useBatchUpload` é estritamente client-side. Nenhum dado de servidor é necessário na montagem inicial desta tela.

### ADR-003: Concorrência com implementação inline — sem `p-limit`

- **Context:** O PRD §02.6.3 especifica upload paralelo com limite de 4 conexões ativas.
- **Decision:** Implementar `uploadWithConcurrency` inline, sem biblioteca externa de concorrência.
- **Reasons:** O PRD §02.6.3 fornece a implementação exata. Adicionar `p-limit` seria uma dependência não aprovada para lógica de 10 linhas.
- **Consequences:** A implementação deve seguir exatamente o padrão worker-queue do PRD §02.6.3.

## 4. Contratos de Interface (State & Hooks)

### 4.1. Tipos e Interface do Estado

```typescript
// Fases do Batch como um todo — mapeamento 1:1 com PRD §02.4.1
export type BatchPhase =
  | 'idle'             // Nenhum arquivo selecionado
  | 'files_selected'   // Arquivos na fila, upload não iniciado
  | 'presigning'       // Solicitando URLs presignadas ao backend
  | 'uploading'        // PUT direto ao Supabase Storage (pool de 4)
  | 'confirming'       // Chamando /batches/{id}/confirm
  | 'success_full'     // Todos confirmados — redirect automático em 2s
  | 'success_partial'  // Concluído com arquivos que falharam no confirm
  | 'presign_error'    // Falha no /batches/presign — lista preservada, retry disponível
  | 'confirm_error';   // Falha no /batches/{id}/confirm — confirm idempotente, retry seguro

// Status de upload de UM arquivo
export type FileUploadStatus =
  | 'idle'       // Aguardando início do upload
  | 'uploading'  // PUT em andamento
  | 'done'       // PUT concluído com sucesso
  | 'error'      // Falha terminal no upload (excluído do confirm)
  | 'expired';   // URL expirada durante upload (renovação em andamento)

export interface FileItemState {
  // Dados do arquivo local
  internalId: string;               // crypto.randomUUID() gerado no cliente na seleção
  file: File;                       // Objeto File original
  validationError?: string;         // Erro de validação local (MIME ou tamanho), se inválido

  // Preenchido após presign bem-sucedido
  documentId?: string;              // UUID do documento vindo do backend
  uploadUrl?: string;               // URL presignada para PUT direto ao storage
  uploadUrlExpiresAt?: string;      // ISO8601 — para detectar 403 de URL expirada (PRD ADR-007)
  objectKey?: string;               // Caminho no storage — usar no confirm (PRD ADR-004)

  // Estado de upload
  uploadProgress: number;           // 0–100
  uploadStatus: FileUploadStatus;
  uploadError?: string;             // Mensagem de erro para exibição no FileListItem

  // Preenchido após confirm
  confirmStatus?: 'confirmed' | 'failed';
  confirmReason?: string;           // Razão de falha do confirm (ex: 'object_not_found')
}

// Estado principal do hook
export interface BatchUploadState {
  phase: BatchPhase;
  batchId?: string;                          // UUID do batch, preenchido após presign
  files: Record<string, FileItemState>;      // Indexado por internalId
  fileIds: string[];                         // Mantém a ordem de adição
  presignErrorKey?: string;                  // Chave i18n do erro do presign (ex: 'errors.rate_limited')
  confirmErrorKey?: string;                  // Chave i18n do erro do confirm (ex: 'errors.server_error')
  rateLimitCountdown?: number;               // Segundos restantes para 429 rate_limit (0 quando liberado)
}
```

### 4.2. Assinatura do Hook Principal

```typescript
/**
 * useBatchUpload
 *
 * Encapsula toda a lógica de estado do upload em lote:
 * validação local, presign, upload paralelo com pool de 4, confirm.
 *
 * PRD referência: §02.5.4
 */
export function useBatchUpload(): {
  state: BatchUploadState;
  addFiles: (files: File[]) => void;          // Valida MIME+tamanho, gera internalId, adiciona ao estado
  removeFile: (internalId: string) => void;   // Remove arquivo da lista (apenas em files_selected)
  submitBatch: () => Promise<void>;           // Inicia o fluxo: presign → upload → confirm
  retryPresign: () => Promise<void>;          // Reinicia o presign com os arquivos válidos (de presign_error)
  retryConfirm: () => Promise<void>;          // Reusa os mesmos document_ids (confirm idempotente, de confirm_error)
}
```

Responsabilidades internas do hook:

1. **`addFiles`**: validação local de MIME e tamanho antes de qualquer chamada de API (PRD ADR-003).
2. **`submitBatch`**: chama presign → ao receber resposta, inicia `uploadWithConcurrency` → ao final, chama confirm.
3. **`uploadWithConcurrency`**: pool de 4 workers, erros capturados por arquivo sem interromper o pool.
4. **Renovação de URL expirada**: ao receber 403 e `uploadUrlExpiresAt` no passado, solicitar nova presigned URL uma vez (PRD ADR-007). Após segunda falha, marcar `uploadStatus: 'error'`.
5. **`retryPresign`**: transita para `presigning`, chama presign novamente com os arquivos sem `validationError`.
6. **`retryConfirm`**: transita para `confirming`, chama confirm com os mesmos `document_ids` de arquivos com `uploadStatus: 'done'`.

## 5. Lógica de Concorrência

Implementação inline conforme PRD §02.6.3 — sem `p-limit` ou outra biblioteca externa:

```typescript
async function uploadWithConcurrency(
  tasks: (() => Promise<void>)[],
  concurrency = 4,
): Promise<void> {
  const queue = [...tasks];
  const workers = Array.from({ length: concurrency }, async () => {
    while (queue.length > 0) {
      const task = queue.shift();
      if (task) await task().catch(() => {}); // erros capturados no nível do FileItemState
    }
  });
  await Promise.all(workers);
}
```

Cada `task` corresponde ao upload de um único arquivo. Erros são capturados internamente e refletem no `FileItemState.uploadStatus` — o pool continua para os demais arquivos.

## 6. Gestão de Estado

### 6.1. Estado local vs servidor

| Dado | Onde vive | Justificativa |
|---|---|---|
| Lista de arquivos e progresso | `BatchUploadState` no hook | Transitório, específico desta sessão |
| `batchId` durante o fluxo | `BatchUploadState.batchId` | Necessário apenas para o confirm |
| JWT do usuário | Supabase JS SDK (`supabase.auth.getSession()`) | Gerenciado pelo SDK, nunca em state local |

### 6.2. Fallback de `sessionStorage` para 401 durante upload

Se o JWT expirar durante `uploading` e o refresh via SDK falhar, o hook deve:

1. Salvar apenas `batchId` no `sessionStorage` (não `uploadUrl` — contém credenciais temporárias).
2. Redirecionar para `/login`.
3. Limpar o `sessionStorage` após uso.

Nunca salvar `uploadUrl` ou `objectKey` no `sessionStorage`.

### 6.3. Sem recuperação automática para upload perdido

Se o usuário fechar o browser durante `uploading`, os uploads são perdidos. O `batchId` ficará em `pending_upload` e será visível na tela de histórico (PRD-03 fase 2). Não há recuperação automática v1.

## 7. Transições de Estado

```
idle → files_selected (addFiles com arquivo válido)
files_selected → idle (removeFile — todos removidos)
files_selected → presigning (submitBatch)
presigning → uploading (presign OK)
presigning → presign_error (4xx/5xx/rede)
presigning → /login redirect (401 irrecuperável)
uploading → confirming (todos os uploads finalizados — sucesso ou falha individual)
confirming → success_full (confirm OK, failed=[])
confirming → success_partial (confirm OK, failed.length > 0)
confirming → confirm_error (5xx/rede no confirm)
presign_error → presigning (retryPresign)
confirm_error → confirming (retryConfirm)
success_full → /batches/{batchId} (redirect automático após 2s)
success_partial → /batches/{batchId} (clique em "Ver batch")
```

---

## 8. Security

1. Nunca serializar `uploadUrl` fora da memória do tab ativo (não em localStorage, sessionStorage, analytics).
2. O JWT é acessado exclusivamente via `supabase.auth.getSession()` antes de cada chamada à API.
3. O `objectKey` enviado no confirm é exatamente o retornado pelo presign — nunca construído no cliente (PRD ADR-004).
4. Arquivos com `validationError` não são incluídos no presign — nunca chegam ao storage.
