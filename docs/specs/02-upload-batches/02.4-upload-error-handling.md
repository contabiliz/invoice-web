# Spec 02.4: Upload Batch — Error Handling & Observability

## 1. Overview

Esta seção define como a Interface do Upload de Batch lidará com exceções tanto do usuário quanto sistêmicas. Em uma ferramenta fiscal enterprise como o Contabiliz, é crítico explicar claramente *o porquê* de uma falha e as opções para mitigá-la (PRD-02).

O módulo define: taxonomia visual de erros (o que é amarelo, o que é vermelho), padrões de renderização de erro por contexto, comportamento offline, e diretrizes de observabilidade sem PII.

---

## 2. Architecture Decision Records (ADRs)

### ADR-001: Mensagens de erro via i18n (`next-intl`)

- **Context:** O sistema precisa suportar internacionalização. As mensagens de erro do upload são o primeiro ponto de entrada para essa necessidade — strings hardcoded bloqueariam a troca de idioma sem deploy.
- **Decision:** Todas as mensagens de erro e labels do upload usam `next-intl`. O hook e os componentes recebem **chaves semânticas** (ex: `upload.errors.rate_limited`) e não strings literais. A tradução é resolvida via `useTranslations('upload')` nos componentes.
- **Reasons:**
  - Strings hardcoded em português tornam impossível adicionar outros idiomas sem alterar código.
  - `next-intl` é o padrão para i18n no Next.js App Router — integração nativa com Server Components e Client Components.
  - Separar chave de tradução do componente facilita revisão de copy sem tocar em lógica.
- **Consequences:** O hook armazena chaves semânticas em `presignErrorKey` / `confirmErrorKey` do `BatchUploadState` (ex: `'errors.rate_limited'`), não strings traduzidas. A tradução ocorre nos componentes via `const t = useTranslations('upload'); t(state.presignErrorKey)`. Os arquivos de mensagens ficam em `messages/pt-BR.json` (e futuros `en.json`). Nenhuma string de UI é hardcoded nos componentes — sempre via `t()`.

### ADR-002: Terminal vs Retryable — dois padrões visuais distintos

- **Context:** Se um arquivo falhar num PUT intermitente, o analista financeiro não deveria descartar o batch inteiro.
- **Decision:** Erros são categorizados em dois padrões visuais e operacionais:
  1. **Retryable / Actionable** (amarelo/azul): erro recuperável com ação disponível ("Tentar novamente").
  2. **Terminal** (vermelho): erro irrecuperável — arquivo deve ser removido ou usuário deve contatar suporte.
- **Reasons:** Clareza operacional. Um contador fiscal que vê "Erro" sem contexto vai reportar bug; ver "Falha de conexão — Tentar novamente" entende o que fazer.
- **Consequences:** Todo componente que exibe erro deve classificar antes de renderizar. A classificação é feita pelo hook antes de propagar ao estado — não nos componentes.

## 4. Taxonomia de Erros e Comportamento

### 4.1. Validação local (pré-voo — ocorre em `addFiles`)

| Situação | Comportamento |
|---|---|
| Tipo MIME não suportado | `FileItemState.validationError = "Tipo de arquivo não suportado."` — arquivo fica na lista como inválido, nunca é enviado ao presign |
| Arquivo > 50 MB | `FileItemState.validationError = "Arquivo muito grande (máx 50 MB)."` — idem |

Apresentação: sem modal. O `FileListItem` do arquivo inválido exibe badge vermelho com a mensagem. `aria-live="polite"` anuncia o erro ao adicionar. A tela continua íntegra.

### 4.2. Erros do presign (`presign_error`)

| HTTP | Mensagem ao usuário | Ação disponível |
|---|---|---|
| 401 | "Sua sessão expirou. Faça login novamente." | Redirect para login |
| 422 | "Arquivo inválido: tipo ou tamanho não suportado." | Erro inline no arquivo |
| 429 (rate limit) | "Muitas tentativas. Aguarde 1 minuto e tente novamente." | Botão com countdown de 60s |
| 429 (backpressure) | "O sistema está ocupado. Tente novamente em alguns instantes." | Botão de retry sem countdown |
| 5xx / rede | "Erro interno. Tente novamente." | Botão "Tentar novamente" |

Apresentação: banner `role="alert"` acima da lista de arquivos. A lista é preservada — o usuário pode editar antes de tentar novamente.

### 4.3. Erros de upload ao Supabase Storage

| Situação | Comportamento |
|---|---|
| 403 + `upload_url_expires_at` no passado | Renovar URL uma vez silenciosamente; em nova falha → `uploadStatus: 'error'` |
| 403 sem URL expirada | `uploadStatus: 'error'`, razão "Permissão negada" — **não renovar** |
| 400 | `uploadStatus: 'error'`, razão "Arquivo inválido" |
| Timeout / rede | `uploadStatus: 'error'`, razão "Falha de conexão" — **sem retry automático** |

Apresentação: o `FileListItem` do arquivo com `uploadStatus: 'error'` exibe fundo avermelhado e razão resumida. Os demais arquivos continuam em upload — um erro individual não cancela o batch (PRD ADR-006).

### 4.4. Erros do confirm (`confirm_error`)

| HTTP | Mensagem ao usuário | Ação disponível |
|---|---|---|
| 404 | "Batch não encontrado. Recarregue a página e tente novamente." | Botão de reload |
| 409 | "Este batch já foi processado." | Redirect para `/batches/{batchId}` |
| 5xx / rede | "Erro interno. Tente novamente." | Botão "Tentar novamente" (confirm é idempotente) |

Apresentação: banner `role="alert"`. Os documentos que tiveram upload bem-sucedido são listados — o usuário sabe o que já foi enviado.

## 5. Network Offline Handling (PRD §02.7.3)

```typescript
// Em useBatchUpload, durante o estado uploading:

window.addEventListener('offline', handleOffline);
window.addEventListener('online', handleOnline);

function handleOffline() {
  // Pausar a fila de uploads (não cancelar — os workers aguardam)
  // Exibir banner "Sem conexão — uploads pausados"
  setPaused(true);
}

function handleOnline() {
  // Retomar a fila
  // Remover banner
  setPaused(false);
}
```

O banner offline tem `role="alert"` e mensagem: "Sem conexão — uploads pausados. Aguardando reconexão…".  
Ao retomar, os arquivos com `uploadStatus: 'uploading'` voltam ao pool de concorrência.

## 6. Padrões Visuais de Erro

### Validações pré-voo (DropZone / FileListItem)
- Sem modal ou toast — erro inline no item da lista
- Badge vermelho + texto da razão
- `aria-live="polite"` ao adicionar arquivo inválido

### Erros de upload individuais (FileListItem)
- Fundo `bg-error-container/20`
- Barra de progresso substituída por texto: `{razão} — TENTAR NOVAMENTE` (botão individual)
- `role="alert"` no container do item em erro

### Erros globais (presign_error, confirm_error, offline)
- `<div role="alert" className="bg-error-container text-on-error-container">` ancorado acima da lista
- Não bloqueia a visualização da lista
- Sempre inclui ação disponível (retry, reload, ou countdown)

## 7. Observabilidade

### 7.1. Eventos a instrumentar (PRD §02.10.1)

```typescript
export interface UploadObservabilityEvent {
  event_type:
    | 'upload_batch_started'
    | 'upload_presign_success'
    | 'upload_presign_error'
    | 'upload_file_completed'
    | 'upload_file_failed'
    | 'upload_confirm_success'
    | 'upload_confirm_error'
    | 'upload_batch_completed';
  // Campos variam por evento — ver PRD §02.10.1 para payload completo
  doc_count?: number;
  total_size_bytes?: number;
  doc_types?: { xml: number; pdf: number; img: number };
  error_code?: string;      // HTTP status ou tipo de erro — nunca o corpo
  latency_ms?: number;
  confirmed_count?: number;
  failed_count?: number;
  total_duration_ms?: number;
}
```

### 7.2. Constraints de segurança no log

1. **Nunca logar:** nomes de arquivos (podem conter CNPJ — ex: `NF_12345678000195.xml`).
2. **Nunca logar:** `upload_url` (contém credenciais temporárias).
3. **Nunca logar:** `object_key` (path do storage do usuário).
4. **Nunca logar:** o JWT.
5. Apenas `doc_type` (xml/pdf/img) e contadores são instrumentados — nunca filename completo.
