### T-SEC-02 — `object_key` enviado no confirm é idêntico ao retornado pelo presign

**Onde:** `useBatchUpload` (teste de integração)  
**Como testar:**
```typescript
it('document_ids no confirm são os document_ids retornados pelo presign', async () => {
  const presignResponse = mockPresignSuccess(3);
  mockPresignBatch.mockResolvedValue(presignResponse);
  
  await act(() => result.current.submitBatch());
  
  const confirmCall = mockConfirmBatch.mock.calls[0][1];
  const expectedIds = presignResponse.documents.map(d => d.document_id);
  // Apenas os que tiveram uploadStatus: 'done'
  expect(confirmCall.document_ids.every(id => expectedIds.includes(id))).toBe(true);
  // O object_key armazenado deve ser o do presign, não construído pelo cliente
  const fileId = result.current.state.fileIds[0];
  expect(result.current.state.files[fileId].objectKey).toBe(presignResponse.documents[0].object_key);
});
```

### T-PERF-02 — Com 4 uploads simultâneos, utilização de banda é superior a uploads serializados

**Onde:** `uploadWithConcurrency`  
**Como testar:**
```typescript
it('4 workers terminam antes de 1 worker serializado para mesma carga', async () => {
  const taskDurationMs = 100;
  const tasks = Array.from({ length: 8 }, () =>
    () => new Promise<void>(res => setTimeout(res, taskDurationMs))
  );
  
  const startParallel = Date.now();
  await uploadWithConcurrency(tasks, 4);
  const parallelMs = Date.now() - startParallel;
  
  // 8 tasks de 100ms com 4 workers = ~200ms (2 rodadas)
  // vs serializado = 800ms
  expect(parallelMs).toBeLessThan(300); // margem para overhead
  expect(parallelMs).toBeGreaterThan(150);
});
```

**Validação complementar:** Observar no DevTools Network com 4 arquivos que 4 PUTs aparecem simultaneamente no waterfall.
