# Spec 02.2: Upload Batch — Camada de Cliente de API (API Client Layer)

## 1. Overview

Esta seção detalha o `BatchApiClient`, que gerencia as interações de rede entre a aplicação frontend e os serviços do backend (`invoice-api`) e o Supabase Storage.

O PRD especifica uma arquitetura de upload presignado (PRD ADR-001):
1. O frontend chama a `invoice-api` (`POST /batches/presign`) para gerar assinaturas.
2. Com as URLs presignadas, o frontend faz upload **diretamente** ao Supabase Storage via PUT.
3. Ao finalizar, o frontend chama a `invoice-api` (`POST /batches/{id}/confirm`) para publicar na fila.

Este módulo NÃO lida com gerenciamento de estado da UI. Sua responsabilidade começa onde o `useBatchUpload` precisa despachar requisições para servidores remotos.

## 3. Architecture Decision Records (ADRs)

### ADR-001: Cliente HTTP — Axios

- **Context:** Precisamos de interceptores de request para injetar JWT e rastrear progresso de upload com `onUploadProgress`.
- **Decision:** Usar Axios para todas as chamadas de rede do upload (presign, PUT ao storage, confirm).
- **Reasons:**
  - `onUploadProgress` do Axios usa XHR internamente — fornece progresso byte a byte em todos os browsers suportados.
  - Interceptores de request simplificam a injeção de JWT sem repetição por chamada.
  - PRD §02.13 exige abordagem consistente — não misturar XHR e fetch. Axios/XHR como escolha única satisfaz essa restrição.
- **Consequences:** Usar Axios em todo o código de upload, sem `fetch` paralelo. O interceptor de auth não deve ser aplicado aos PUTs ao Supabase Storage (a presigned URL já contém as credenciais).

### ADR-002: Autenticação — Supabase SDK via interceptor Axios

- **Context:** O JWT deve ser fresco antes de cada chamada à `invoice-api`.
- **Decision:** `axios.interceptors.request.use` chama `supabase.auth.getSession()` e injeta o token fresco no header `Authorization: Bearer <token>` antes de cada request à API.
- **Reasons:** O SDK do Supabase gerencia refresh automático. Chamar `getSession()` no interceptor garante token sempre fresco sem lógica manual de expiração.
- **Consequences:** O interceptor deve ser aplicado apenas à instância Axios da `invoice-api`, não à instância usada para os PUTs ao storage (que não levam JWT).

### ADR-003: Tipos manuais — sem geração via OpenAPI

- **Context:** O PRD §02.3.2 referencia `import type { components } from "@/types/api"` gerados por CI. O usuário optou por tipos manuais.
- **Decision:** Os DTOs são mantidos manualmente em `src/lib/api/types.ts`. O dev frontend é guardião do alinhamento com a `invoice-api`.
- **Reasons:** Início mais rápido sem exigir que o schema OpenAPI da `invoice-api` esteja disponível no CI. Adequado para a fase atual do projeto.
- **Consequences:** Se a `invoice-api` mudar um campo, o frontend pode divergir silenciosamente. Risco mitigado por testes de integração que exercitam o contrato real (T-FUNC-02 no plano de testes).

## 5. O `BatchApiClient`

### 5.1. Instâncias Axios

```typescript
// Instância para chamadas à invoice-api — leva JWT via interceptor
const apiClient = axios.create({
  baseURL: process.env.NEXT_PUBLIC_API_URL,
});

apiClient.interceptors.request.use(async (config) => {
  const { data: { session } } = await supabase.auth.getSession();
  if (session?.access_token) {
    config.headers.Authorization = `Bearer ${session.access_token}`;
  }
  return config;
});

// Instância para PUTs ao Supabase Storage — sem JWT (presigned URL já tem credenciais)
const storageClient = axios.create();
```

### 5.2. `presignBatch`

**Endpoint:** `POST /api/v1/batches/presign`  
**Payload:** `BatchPresignRequest`  
**Response:** `BatchPresignResponse` (HTTP 202)

```typescript
export async function presignBatch(
  request: BatchPresignRequest,
): Promise<BatchPresignResponse>;
```

### 5.3. `uploadFileToStorage`

**Operação:** `PUT <upload_url>` — direto ao Supabase Storage, sem JWT.

```typescript
export async function uploadFileToStorage(
  uploadUrl: string,
  file: File,
  onProgress: (percent: number) => void,
): Promise<void>;
```

- Usa `storageClient` (sem interceptor de JWT).
- Usa `onUploadProgress` do Axios para calcular `percent` (0–100).
- Erros 403: tratados no `useBatchUpload` (PRD ADR-007) — esta função apenas lança o erro.

### 5.4. `confirmBatch`

**Endpoint:** `POST /api/v1/batches/{batchId}/confirm`  
**Payload:** `BatchConfirmRequest`  
**Response:** `BatchConfirmResponse` (HTTP 200)

```typescript
export async function confirmBatch(
  batchId: string,
  request: BatchConfirmRequest,
): Promise<BatchConfirmResponse>;
```

- Confirm é idempotente — seguro chamar novamente em caso de `confirm_error` com os mesmos `document_ids`.
- Recebe apenas `document_ids` com `uploadStatus: 'done'` — arquivos com `uploadStatus: 'error'` são excluídos pelo hook antes de chamar esta função.

## 6. Error Taxonomy do API Layer

### Terminal (propaga para o hook, sem retry automático nesta camada)

| Situação | Status | Ação no hook |
|---|---|---|
| JWT expirado sem refresh | 401 | Salvar `batchId` no `sessionStorage`, redirecionar para login |
| Arquivo inválido (bypass de validação local) | 422 | Marcar arquivo como `validationError`, transitar para `presign_error` |
| Permissão negada no storage (URL não expirada) | 403 (storage) | Marcar `uploadStatus: 'error'` — não renovar URL |
| Arquivo inválido no storage | 400 (storage) | Marcar `uploadStatus: 'error'` com razão "Arquivo inválido" |
| Batch não encontrado | 404 (confirm) | Transitar para `confirm_error` — mensagem "Batch não encontrado. Recarregue e tente novamente." |
| Batch já processado | 409 (confirm) | Redirecionar para `/batches/{batchId}` sem erro |

### Retryable (o hook trata via `retryPresign` / `retryConfirm`)

| Situação | Status | Ação no hook |
|---|---|---|
| Servidor indisponível (presign/confirm) | 502/503/504 | Transitar para `presign_error` ou `confirm_error` |
| Rate limit ou backpressure | 429 | Transitar para `presign_error` — mensagem diferenciada por `detail` |
| URL presignada expirada | 403 + `upload_url_expires_at` no passado | Renovar URL uma vez; após segunda falha → `uploadStatus: 'error'` |
| Timeout/rede no upload | Timeout | Marcar `uploadStatus: 'error'` com razão "Falha de conexão" — **sem retry automático** |

**Distinguir 429 rate-limit vs backpressure (PRD §02.7.1):**  
- `detail` contém "rate limit" → mensagem: "Muitas tentativas. Aguarde 1 minuto." (countdown 60s)  
- Caso contrário → mensagem: "O sistema está ocupado. Tente novamente em alguns instantes."

## 7. Security Constraints

1. Nunca logar o JWT, `upload_url` ou `object_key` em console ou serviços de telemetria.
2. `storageClient` nunca recebe o header `Authorization` com o JWT da aplicação.
3. Não fazer replay de upload se o presign retornar 422 — pode indicar tentativa de spoofing.
4. Filenames não são enviados a serviços de analytics — apenas `doc_type` e contadores (PRD §02.8).
